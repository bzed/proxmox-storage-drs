# `tests/corpus/` — real-cluster diagnostic bundles

This directory holds **anonymized diagnostic bundles collected from real Proxmox VE
clusters**, and it is part of the test suite. `IMPLEMENTATION_PLAN.md` section 16 is the
specification for everything here; this file is the operational side of it.

A bundle is produced by an operator on their own cluster:

```sh
pve-storage-drs -c /etc/pve/drs.yaml collect-testdata
```

and is replayed by the engine with no network access at all:

```sh
pve-storage-drs --replay tests/corpus/<bundle-name> plan --json
```

**Status: implemented** — phase 10 of section 12, section 16 is the specification.
`bzed-dev-cluster-24h` is the first bundle, collected from the project's own dev cluster
(see `bzed-dev-cluster-24h.submission.yaml`). `bzed-dev-cluster-7d-holt-winters` is the same
cluster with a 7-day window, and `bzed-dev-cluster-free-space` is the first bundle captured
*after* phase 13 (section 5.3.1): all three shared storages in the group, a different resolved
`free_space` soft/hard pair on each, and a plan that is a repair. The first two predate phase 13
and still carry the deprecated `snapshot_reserve.min_free_bytes` scalar in their `config.yaml` —
deliberately left as captured, since they are the proof that a bundle from before `free_space`
existed still replays. An empty corpus is still a clean pass: the
test suite is green on a fresh clone even with no bundles in it, so a bundle here is
additional coverage, not a dependency.

## Why real bundles

Every interesting failure this tool has had so far was found by an operator running it on
a cluster the author has never seen, and then *describing* what they saw — one metric
silently missing for a single disk, `/content` returning an empty list under
`Datastore.Audit` alone, a coverage query starved by a `window.lookback` set too close to
`metrics.step`. A description is not a regression test. A bundle is: it is the shape of
data that produced the failure, replayable offline, forever.

The second reason is the one no synthetic fixture can cover. `tests/fixtures/fc-tier1.yaml`
proves the solver optimal by enumerating all 3^6 assignments; a real cluster has hundreds
of disks and no enumerable answer. What a real bundle can prove is that the MILP and the
heuristic still agree about feasibility and about the objective at that scale — see
"What the suite asserts" below.

## Layout

```
tests/corpus/
  README.md
  <bundle-name>/                 # the unpacked bundle directory, exactly as collected
  <bundle-name>.submission.yaml  # provenance and consent — required
  <bundle-name>.expected.json    # generated by validate_corpus.py, never hand-edited
  validate_corpus.py             # the generator and the --check gate
```

The **unpacked directory** is the committed form, not the tarball: it diffs line by line in
review, it compresses well in git, and the scrub audit reads it as plain files.

## Adding a bundle

0. **Work under `tests/corpus/local/` while reviewing.** It is gitignored (scratch space for
   "being reviewed before committed or discarded", and for anything too big to commit —
   point `DRS_CORPUS_DIR` at it). A bundle sitting directly in `tests/corpus/` with no
   submission file yet is an unattributed dump *in the committed-bundle namespace*, and the
   scrub/submission gate below fails on it correctly — that failure is not "unrelated" or
   "pre-existing" the way REVIEW.md's Z-07 finding shows a 0.1.3 release commit message once
   treated it; it means the bundle is in the wrong place. Move it into `tests/corpus/`
   proper — with its submission file — only once you are ready to commit it.
1. **Read it first.** Open the directory. It is sorted, indented JSON, meant to be read.
   `manifest.json` says what was captured and what failed; `config.yaml` is the
   configuration the run used with its credentials removed.
2. Write `<bundle-name>.submission.yaml` (see the template below). A bundle without one is
   an unattributed dump, not a test case, and the suite fails on it.
3. Run the audit and the generator:
   ```sh
   python3 tests/corpus/validate_corpus.py            # regenerate expectations
   python3 tests/corpus/validate_corpus.py --check     # assert they are current (what CI runs)
   make corpus                                         # the full variant matrix
   ```
4. Commit the bundle directory, its submission file and its expected file together.

### Repairing an already-committed bundle

Sometimes the collector itself had a privacy bug (REVIEW.md Z-01 is the first instance: a
Telegraf `host` tag reached two committed bundles' `findings.json` before the fix that strips
it). A committed bundle is real captured data, not something to hand-edit freely, so a repair
follows a narrower path than "adding a bundle":

1. Fix the collector first, with its own regression test.
2. Rebuild the affected derived file (`findings.json`, `config.yaml`, ...) **from the
   bundle's own already-captured, already-anonymized data**, with the fixed code — never by
   inventing or guessing a replacement value. For a `findings.json` message that duplicates a
   structured field (the sample-series-labels shape Z-01 fixed), the structured field itself
   is the source of truth: the fix is mechanical, needs no salt, and is byte-verifiable
   against it.
3. Recompute `SHA256SUMS` for every file the repair touched.
4. Verify: the scrub audit (plus any new shape check the fix added) passes, and
   `validate_corpus.py --check` still exits 0 without needing to regenerate the bundle's own
   `.expected.json` — a repair that changes `findings.json`'s *content*, not the plan the
   bundle produces, should not need to.
5. Record the repair in the bundle's own `<bundle-name>.submission.yaml` (a short note: what
   leaked, which commit fixed the collector, which commit repaired the bundle) — so the
   history of what a committed bundle once contained stays honest and discoverable, rather
   than disappearing into a silent diff.

### Size ceiling, and bundles too big to commit

A committed bundle must be **under 8 MiB unpacked**. At section 16.2's estimate that is a
cluster of a few dozen disks, or a `--no-series` capture of a large one.

Anything bigger stays outside the repository. The suite also walks every directory named in
the `DRS_CORPUS_DIR` environment variable (colon-separated), so a large corpus can live on
the author's machine or on a CI runner without bloating git history. Bundles found that way
are exercised exactly like committed ones.

### `<bundle-name>.submission.yaml`

```yaml
submitted_by: Somebody <somebody@example.org>   # or "anonymous", with a contact for questions
submitted_on: 2026-09-11
consent:
  redistribute_under: AGPL-3.0-or-later          # same terms as the rest of this repository
  reviewed_bundle_before_sending: true           # the submitter opened it and read it
collected_with: pve-storage-drs 0.1.1            # the collector version, from manifest.json
versions:
  pve: 9.2.11
  prometheus_backend: gigapipe                   # or prometheus, victoriametrics, ...
what_this_reproduces: >
  One of the six blockstat metrics missing for a single disk while the other five
  report it normally — the Telegraf non-numeric-field drop of section 3.3.
```

## What the suite asserts

Four kinds of assertion, in the order they run:

1. **The scrub audit** — runs on every bundle on every `make check`, before anything else.
   It fails on any key outside `anonymize.py`'s allowlist (the same allowlist the collector
   uses, so the two cannot drift), on any value matching an IP literal, an email address, an
   `iqn.`/`naa.`/`wwn.` prefix, a PEM block, a long hex run, a public-suffix hostname or a
   JWT shape, on any node or storage name that is not a valid pseudonym, and on any
   timestamp outside the bundle's synthetic epoch window. It assumes the collector has a
   bug, which is the only useful assumption to make about a privacy control.
2. **Invariants, not optima.** The reserve is satisfied wherever a reserve-feasible
   assignment exists; section 8.1's transient predicate holds at every step of the emitted
   order; every move targets a storage (C2) permits for that disk; section 7.3's per-move
   duration rule and saturation guard hold for every accepted move; the objective handed to
   the scheduler equals the objective recomputed from the final assignment.
3. **MILP versus heuristic on real data.** CP-SAT, CBC and the heuristic solve the same
   bundle; the MILP objective must be `<=` the heuristic's, and the two MILP backends must
   agree within section 5.5's tolerance. A heuristic that beats the MILP means the shared
   feasibility or objective functions have drifted apart — the thing `AGENTS.md` section 5
   exists to prevent, and the thing only a large real instance can detect.
4. **Regression.** `<bundle-name>.expected.json` records, per variant, the gate verdict, the
   plan, the order, the objective breakdown, the payback arithmetic and the findings. It is
   **generated**: never hand-edit it. An expected file a human may edit is one that will
   eventually be edited to match a bug.

The variant matrix per bundle is `solver.backend` × `objective.spread_metric` ×
`forecast.model` × a short `objective.beta_move_count` sweep. A variant whose backend or
forecaster is not installed is **recorded as skipped**, never silently dropped — CP-SAT is an
optional dependency, and a corpus result that quietly means "CBC only" is a corpus result
that lies.

## What a bundle does and does not hide

A bundle carries **no direct identifier and no secret**: no hostname, no IP address, no IQN,
no PBS fingerprint, no key, no password, and none of the operator-authored free text — VM
names, descriptions, snapshot names, storage comments, notes — where those tend to live.
Identifiers are replaced by pseudonyms keyed to a salt that stays on the submitting host and
never enters the bundle, so the same cluster maps to the same names across bundles while the
mapping cannot be inverted by anybody who receives one.

It is **not anonymous against somebody who already knows the cluster.** Node, storage and VM
counts, capacities, disk sizes and load shapes all survive, because they are what makes a
bundle a test case rather than a shape, and together they are a fingerprint: a cluster with
three nodes, two 8 TiB LUNs and 1214 VMs is recognizable to anyone who has seen it.

So, both directions of the exchange:

- **Submitting** a bundle to the author is an informed decision, not a formality. Read it
  first. If your cluster is one whose mere size and shape is confidential, say so and send a
  `--no-series` bundle, or nothing at all — a description is still worth having.
- **Accepting** one into this repository makes it public, permanently, in git history. That
  needs the submitter's explicit consent, which is what `submission.yaml` records, and it
  needs the scrub audit to pass. A bundle whose submitter did not review it does not get
  committed, however clean the audit says it is.
